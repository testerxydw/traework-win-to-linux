# 2026-08-31

## WorkBuddy 构建脚本：完全脱离社区移植版 deb

### 背景
用户要求 `build-workbuddy.sh` 完全不再依赖社区移植版 deb（`cn.workbuddy.otohime_*.deb`），
运行时优先用下载的官方 Electron 或本地缓存，原生模块从 npm 源码编译。

### 关键技术结论（重要）
- **官方 Electron 39.2.7 的 ABI = 136**。WorkBuddy 5.3.14 原生模块必须匹配此 ABI。
- **社区 deb 里的原生模块其实不可用**：
  - better-sqlite3 是 ABI 140（不匹配 Electron 39 的 136）
  - qimei.node 是 invalid ELF（损坏/占位）
  - 之前 daemon SIGSEGV 问题可能正源于此
- **真正可用的是 `workbuddy-build/linux_native/`**：better-sqlite3 是 ABI 136（之前 electron-rebuild 编译的）
- **koffi 是 N-API 8**（ABI 稳定），任何 Node/Electron 都能加载。从 npm 拉源码 + `node src/cnoke/cnoke.js -P . -D src/koffi --prebuild` 编译出 `linux_x64/koffi.node`
- **node-pty** 是 prebuild 包（Node ABI 115），无 gyp 无法编译成 Electron ABI，是 optionalDependency，功能受限
- **qimei-node** 是 optionalDependency，无 Linux 源码，跳过

### 脚本改动
- 移除所有社区 deb 解包逻辑（`COMMUNITY_DEB`/`COMM_UNPACKED`/`community_extract`）
- 运行时来源优先级：`--runtime` → 下载官方 Electron 39.2.7（npmmirror/GitHub）→ 本地缓存
- 新增原生模块准备阶段（2a）：复用 `linux_native/` 的 better-sqlite3 + npm 编译 koffi + npm 拉 node-pty
- 修复 `stage_deb` bug：`[[ -f CONTROL_FILE ]] || die` 在生成逻辑之前，导致 control 不存在时直接 die（已删除该 die）
- npm install 需先 `npm init -y` 再 install（`--no-save` 在无 package.json 目录不实际安装）

### 验证结果
- 完整流程跑通，产物 `workbuddy_5.3.14-2_amd64.deb`（132M）
- 安装成功，启动成功（退出码 0，仅无害 GLib 警告）
- 产物原生模块 ABI 验证：better_sqlite3=ABI136 ✓，koffi=LOADED OK ✓，pty=LOADED OK ✓

### 缓存目录（复用，避免重复下载/编译）
- `workbuddy-build/runtime-cache/`：官方 Electron 39.2.7 运行时
- `workbuddy-build/native_build/`：npm 编译的 koffi
- `workbuddy-build/linux_native/`：ABI 136 的 better-sqlite3

### 桌面文件缺失修复（重要）
- **问题**：新版运行时是官方 Electron（不含 .desktop 文件），旧脚本 3f 步骤用
  `find "$RUNTIME_ROOT" -name '*.desktop'` 找 desktop，官方 Electron 里没有 → desktop 未生成。
- **修复**：desktop 文件改为**脚本自己生成**（heredoc 固化标准内容，Exec=workbuddy, Icon=workbuddy），
  不再依赖运行时目录。图标优先用 Windows 源 `resources/app.asar.unpacked/resources/icon.png`，
  其次运行时缓存。
- **验证**：新版 `workbuddy_5.3.14-3_amd64.deb` 含 desktop + 图标 + /usr/bin 入口，安装后桌面文件正常显示。

### 页面空白/缺文件修复（关键）
- **问题**：重构后 3d 只复制了自编译的 3 个 Linux 原生模块到 `app.asar.unpacked/node_modules/`，
  **丢弃了 Windows 源 unpacked 的 cli/native/resources 顶层目录和 bindings/file-uri-to-path/@tencent
  等运行期依赖** → 新包仅 295 文件/132M（旧包 1493 文件/165M），启动后 renderer 报
  `MODULE_NOT_FOUND`（requireStack 指向 app.asar/main/workbuddy-auth-product-coordinator.js），页面空白。
- **修复**：3c-2 步骤**整体复制 Windows 源 `app.asar.unpacked`**（保留 cli/native/resources 与完整
  node_modules），再在 3d 用**外科手术式覆盖**仅替换运行期必需的 5 个 Linux 包
  （better-sqlite3 / bindings / file-uri-to-path / koffi / @lydell）。
  3d-2 清理纯 Windows/macOS 二进制（.exe/.dll/.pdb/.dylib/.framework/.app）缩体积。
- **验证**：重建后 1483 文件/165M，unpacked 目录结构与旧包**完全一致**
  （顶层 cli/native/node_modules/resources；node_modules 含 better-sqlite3/bindings/
  file-uri-to-path/koffi/@lydell/node-pty/@tencent），日志无 MODULE_NOT_FOUND。
- **教训**：`app.asar.unpacked` 是运行期依赖集合，**不能只塞自编译模块**，必须以 Windows 源为基底整体搬入，
  再用 Linux 产物覆盖同名的运行期必需包。

## trae-solo-cn 0.1.58 标题栏 + work 模式回显修复

### 问题1：标题栏不是系统原生（native）
- **根因**：`resources/app/out/main.js` 里配置层 `getValue("window.titleBarStyle")` 硬编码返回
  `"custom"`，覆盖 product.json 与用户设置，导致 DDE 下不显示系统标题栏。
- **修复**（build.sh main.js 补丁，宽松独立命中，不依赖具体 minify 函数名）：
  1. 标题栏解析函数（`oW` 旧 / `hV` 新）插入 `if(Lt)return"native"`（Lt=isLinux）
  2. `titleBarOverlay` 设置加 `Lt||` 守卫（Linux 跳过，避免白块）
  3. 配置层 `switch(i){case"window.titleBarStyle":return"custom"}` 改为
     `return this.a.getValue("window.titleBarStyle",e,void 0)||"native"`
- **双保险**：launcher 加 `--title-bar-style=native`（Chromium 标准参数，优先级最高）

### 问题2：work 模式 AI 输出不实时刷新（需切页才显示）
- **现象**：work 模式执行中无实时进度回显，完成后必须切换页面才看到 AI 回复。
- **根因**：DDE（X11）下 Electron 窗口遮挡检测/后台节流误判窗口被遮挡，暂停渲染重绘。
- **修复**：launcher `EXTRA_ARGS` 加
  `--disable-backgrounding-occluded-windows --disable-renderer-backgrounding --disable-background-timer-throttling`
  （附带 `--disable-dev-shm-usage`）。
- **验证**：进程参数已确认传入，`_NET_WM_WINDOW_TYPE=NORMAL`（标准系统窗口）。回显修复需用户在 GUI 实测 work 模式。

- workbuddy: 5.3.14-2 → -3(桌面修复) → -4(清理 wb_pkg 残留目录 app.asar.unpacked/app_asar_extract)

## trae-solo-cn work 模式回显排查结论（最终版，用户直接观察为准）

### 用户最终准确描述
- **code 模式（solo_agent_lite）**：初始化后**持续输出内容**（实时）✓
- **work 模式（solo_work_lite）**：**初始化频繁**（每 30-50ms 一次 `Initializing session`），但**不实时显示内容**，结束后才整体呈现 ✗

### 日志实证（session `6a8e7d771333de295741572f` = work 模式）
work 模式流式是**分段短流循环**，不是单条长流：
```
16:33:01.806  Stream started
16:33:03.153  Stream completed   (仅 1.3s 就 completed)
16:33:03.162  finalizeStream
16:33:03.208  Initializing session  ← 重新 init
16:33:03.xxx  Initializing ×N（每 30-50ms，疯狂）
16:33:05.577  Setting messages (planItemCount 17→13)
16:33:05.687  Stream started (again)
16:33:05.928  Stream completed   (又一次 1.3s)
... 循环约 5 次
```
对比 code 模式：单条长流，`Stream started` 后持续不 completed，组件稳定挂载 → 实时。

### 根因
work 模式的流式被拆成多个短片段（每个 plan step/子任务一段流），每段结束触发
`finalizeStream` + 会话 `Initializing`（重建聊天组件），把正在显示的内容冲掉；
下一次 `Stream started` 时组件刚重建，内容又从头来 → 视觉上"频繁初始化但不显示"。
这是 **solo-lite 前端对 work 模式多轮/多步流式处理逻辑**，非 Electron/打包问题
（code 模式实时证明渲染管线 + `--disable-*` 参数均正常）。

### 结论
- 非移植 bug，是官方前端 work 模式行为；改需动 minified `solo-lite/dist/0e46605bb96ad360.js`（328K），
  精确定位风险高、升级即失效 → 按用户指示暂不修。
- 之前分析曾两次把 code/work 归属搞反，**以本段「用户直接观察 + 日志时间线」为准**。

# 2026-09-01

## WorkBuddy 移植版：退出后进程残留（孤儿进程）根因分析

### 现象
用户关闭页面后 `/opt/workbuddy` 下残留多个进程，PPID 全为 2188（`systemd --user`）→ 父进程已死的孤儿。

### 实测证据（11:52 那批，main 887597 已退出）
- `890281 workbuddy-bin --type=zygote --no-sandbox`（2.8% MEM，空转烧 CPU）
- `889923 /proc/self/exe --type=utility --utility-sub-type=network.mojom.NetworkService`
- `891506 workbuddy-bin .../main/daemon-app-server-entry.js --stdio`
- `896002 sidecar-entry.js --token ...`（daemon 子）
- `1408713 .../cli/bin/codebuddy --prewarm --prewarm-id wb-pool-...`（daemon 子，detached）
- 对比活的 1155625 批次：所有 zygote/daemon PPID 均指向 1155625，结构完整
- 注意：1155625 主进程窗口其实还在开（xdotool 266338308, 屏幕0 @307,138），用户以为已退出

### 三层根因
1. **Chromium 子进程未被回收**：主进程走非优雅退出（app.exit/崩溃/被杀），
   `ChildProcessLauncher` 未 kill 子进程；Linux 下 zygote 靠 mojo IPC 感知 browser 存活，
   browser 异常终止收不到通知，也不收 SIGHUP → 残留。
2. **daemon 无"父进程失联"兜底**：`daemon-app-server-entry.js`（51 行）完全没有
   `process.stdin` 的 'close'/'end' 监听；`daemon-app-server-main.js` 只在 705-706 行注册
   `SIGTERM`/`SIGINT` 的 shutdown。主进程死后继续 `writeDaemonStdioFrame` →
   `write EPIPE` 变成 uncaught exception（crash-report-daemon-891506 证实），只记录不退出，
   AppStartup.log 满屏 EPIPE 刷屏。
3. **prewarm 池 `detached: true` 逃逸**：`cli-prewarm-pool.js:2321`
   `spawn(execPath, [cliPath,'--prewarm','--prewarm-id',id], { detached: true, stdio:['ignore',...] })`
   → Linux setsid 新会话，父死不被回收。池还会 `scheduleReplenish` 自动补员
   （日志 1 秒 spawn 4 个：`prewarm IPC not ready in time` ×3）。
   官方清理只在 dev 路径 `dev-env-actions2.js:108` `pkill -f "codebuddy.*--prewarm"`。
   `CliPrewarmPool.stop()`（2259 行）能 kill 全部，但需主进程优雅 shutdown 才调用到。

### 为什么 Windows 版不明显（移植特有）
- `--type=zygote` 是 Unix 独有，Windows 无 zygote 进程 → 第 1 类残留 Linux 独有
- Windows Electron 用 Job Object 管子进程树，主进程终止 OS 自动清树；Linux 无等价物

### 修复方案（A+B，已实施并落地）

#### A 代码层：`workbuddy-build/scripts/patch-daemon-lifecycle.py`（新增）
- `main/initialize.js` 的 `writeDaemonStdioFrame` 包 try/catch，捕获同步抛出的 EPIPE
  → 调 `globalThis.__workbuddyDaemonStdioGone()`
- `main/daemon-app-server-main.js` 在 `process.on("SIGINT", shutdown)` 后注入
  `shutdownOnHostGone(reason)`：置 `globalThis.__workbuddyDaemonHostGone` 防重入 →
  先 `daemon.cliPrewarmPool.stop()` 杀光 detached prewarm → `lifecycle.shutdown()`
  → `process.exit(0)`，3 秒 `setTimeout` 兜底（unref）
- 监听：`stdin 'end'/'close'`（优雅退出时 EOF）+ `stdin.resume()` + `stdout 'error'`（崩溃时 EPIPE）
- 幂等：以补丁标记 `NEW_* in content` 判断，重复执行不增大文件

#### B launcher 层：`workbuddy_cleanup_orphans()`（在 /opt/workbuddy/workbuddy 内）
- **归属判定用 `/proc/<pid>/exe == /opt/workbuddy/workbuddy-bin`**。
  不能只 grep 命令行：Chromium 子进程 argv[0] 是 `/proc/self/exe`，命令行里没有 APP_DIR
  （实测会漏掉 network.mojom.NetworkService）
- **主进程判定**：无 `--type=` 且命令行不含 `app.asar`。
  若只判 `workbuddy-bin` + 无 `--type`，会把 `codebuddy --prewarm` 误判成主进程
- **孤儿判定**：沿 PPID 祖先链（最多 32 层）找不到任何活着的 main → 孤儿。
  循环 3 轮清级联（daemon 被杀 → sidecar/prewarm 变孤儿）
- 只杀子服务特征：`--type=(zygote|utility|renderer|gpu-process)`、`daemon-app-server-entry.js`、
  `sidecar-entry.js`、`--prewarm`。crashpad（exe 不同）与主进程自身均不匹配 → 安全
- 实测：准确识别 5 个孤儿，运行中的实例 9 个进程一个没误伤

#### 打包脚本集成（`build-workbuddy.sh`）
- 新增 `--patch-asar <file>`：单独对 app.asar 打补丁（修已安装环境，免重建）
- `patch_app_asar()` 放在**主流程** stage_extract 之后（不在 stage_extract 内），
  这样 `--skip-extract` 复用旧 wb_pkg 时也生效，且幂等可重复
- launcher 改为**每次构建无条件覆盖写入**（原来 `if [[ ! -f ]]` 只在不存在时生成，修复推不动）

### 关键技术结论：asar 原地替换（重要）
整体 extract → patch → repack 不可行：
1. extract 需要 `app.asar.unpacked/` 完整，已安装环境缺
   `cli/vendor/ripgrep/x64-linux/rg` → 直接 ENOENT 失败
2. repack 会**丢失 unpacked 标记**，把 `.node`/`rg` 等塞回 asar → 运行时无法 spawn

asar 3.x 布局（已实测验证）：
```
[0:4]  uint32 = 4                    (sizeBuf pickle payload_size)
[4:8]  uint32 = headerBuf.length     ← size
[8:8+L] headerBuf = pickle(string headerJSON)
         [0:4] pickle payload_size
         [4:8] uint32 = json 字节长度
         [8:8+n] header JSON（UTF-8）
         padding 到 4 字节（0x00）
base = 8 + headerBuf.length；条目 offset 相对 base，offset 存成**字符串**，size 是 int
```
- 替换做法：新内容追加到数据区末尾，改该条目 offset/size/integrity；
  header 长度变化 delta → 其余条目 `offset -= delta`；迭代 8 次收敛（实测 delta=0）
- **integrity 必须重算**（asar/lib/integrity.js 语义）：
  `hash = sha256(整个文件)`；`blocks = 每个满 4MB 块的 sha256 hex`，
  **flush 时无条件再补一个尾块**（含空块）。注意 hash 不是 blocks 摘要的拼接
- 验证结果：条目数 17221 不变、随机抽样 40 个文件字节一致、integrity 自校验通过、
  两个文件 `node --check` 通过、重复执行幂等

### 落地状态
- 已安装环境：5 个孤儿已 `kill -9` 清理；`/opt/workbuddy/resources/app.asar` 已打补丁
  （备份 `app.asar.bak-prepatch`）；`/opt/workbuddy/workbuddy` 已换新 launcher
- **待用户重启 WorkBuddy 生效**——当前实例（1155625）加载的是旧代码，daemon 不会自杀
- 验证方法：重启后关闭窗口，`ps -ef | grep workbuddy` 应只剩 0 个（或下次启动时被 launcher 清理）

## WorkBuddy 移植版：托盘右键菜单不显示

### 根因（已修复）
`main/index.js` 的 `initializeTray()`（约 18616 行）实现了托盘 + `buildFromTemplate` 的
contextMenu（显示窗口 / 退出），但**只监听 `tray.on("right-click", popUpContextMenu)`，
没调用 `tray.setContextMenu(menu)`**。

- Windows/macOS：`right-click` 事件触发 → 菜单正常弹出
- **Linux 走 libayatana-appindicator**：AppIndicator 协议只暴露「激活」信号，Electron 在
  Linux **不发送 right-click 事件**；菜单必须经 DBusMenu（`com.canonical.dbusmenu`）由
  dde-dock 主动请求，而 DBusMenu 的暴露依赖 `setContextMenu`。两条件都不满足 → 图标在、菜单出不来

### 修复
Linux 下补 `if (process.platform === "linux") this.tray.setContextMenu(contextMenu);`
Windows/macOS 路径不变（仍靠 right-click）。锚点：
`this.tray.on("right-click", () => this.tray?.popUpContextMenu(contextMenu));`

### 落地
- 新增 `workbuddy-build/scripts/patch-tray-linux.py`（复用 asar 原地替换框架，`import patch_daemon_lifecycle as pdl`）
  - 注意：原 `patch-daemon-lifecycle.py` 已重命名为 `patch_daemon_lifecycle.py`
    （连字符文件名无法被 Python import），`build-workbuddy.sh` 的 `PATCH_SCRIPT` 引用已同步
- `patch_app_asar()` 现在顺序调用两个补丁脚本（进程回收 + tray）
- 已验证：daemon+tray 两补丁叠加后条目数 17221 不变、随机抽样 30 文件字节一致、3 文件 integrity 正确、`node --check` 通过
- 已应用到 `/opt/workbuddy/resources/app.asar`（与 daemon 补丁叠加）
- **✅ 已验证生效**：用户重启后确认 DDE 下右键托盘图标弹出菜单且功能正常

## build-workbuddy.sh：桌面图标错误（"中国移动"横幅）— 根因 + 修复

### 现象
新打出来的 deb（`-3`）装好后，桌面/dock 上 WorkBuddy 图标是 **867x250** 的横幅
"中国移动 China Mobile | WorkBuddy"，而不是原版 WorkBuddy 1024x1024 方形 logo。

### 根因（已修）
`build-workbuddy.sh` 第 385-398 行的图标优先级反了：

```bash
COMM_ICON="$(find "$RUNTIME_ROOT" \( -name '*.png' -o -name '*.svg' \) 2>/dev/null | head -n 1)"   # ← 社区 runtime 下的"中国移动"横幅
WBSRC_ICON="$WBSRC/resources/app.asar.unpacked/resources/icon.png"                                # ← 真正的 WorkBuddy 1024x1024
if [[ -n "$COMM_ICON" ]]; then
    cp -f "$COMM_ICON" .../workbuddy.png        # ← 命中，复制了横幅
elif [[ -f "$WBSRC_ICON" ]]; then
    cp -f "$WBSRC_ICON" .../workbuddy.png        # 永远走不到
fi
```

`RUNTIME_ROOT`（社区版 `cn.workbuddy.otohime_*.deb` 解出来的 `runtime-cache/files/`）下的第一个
png 是 867x250 横幅；`WBSRC`（Windows 源 `WorkBuddy-win32-x64-user-*.exe` 解出来）的
`app.asar.unpacked/resources/icon.png` 才是真正的纯 WorkBuddy 1024x1024 方形 logo。

### 修复
改为「优先 Windows 源，fallback 才用 RUNTIME_ROOT」（commit 见 build-workbuddy.sh:386-401）：
```bash
if [[ -f "$WBSRC_ICON" ]]; then
    cp -f "$WBSRC_ICON" .../workbuddy.png
elif [[ -n "$COMM_ICON" ]]; then
    cp -f "$COMM_ICON" .../workbuddy.png 2>/dev/null || true
fi
```

### 关键环境约束（已装环境的坑）
deepin v25 把 `/usr` 整体做成 **ro overlay**：
```
/usr usr-overlay overlay ro,relatime,
  lowerdir=/root/persistent/overlay/data/layer-83aeed.../usr:...,
  upperdir=/root/persistent/overlay/data/layer-67024.../usr
```
→ `sudo cp /usr/share/icons/.../workbuddy.png` 直接 `EROFS: 只读文件系统`，连删都删不掉。
workbuddy.png 是 9/1 15:00 dpkg 装 `-3` 时写入的（当时 overlay 还是 rw），现在保护层切到 ro。

参考其他应用的做法：
- linglong 应用（motrix / youdao / xmind）：图标实体放 `/opt/apps/<id>/entries/icons/...`，
  `/usr/share/icons/.../apps/<name>.png` 做成 symlink → 实体（但 symlink 也是 ro，无法手工建）
- 普通 dpkg 应用：实体直写 `/usr/share/icons/...`（ro 下装包会失败）

### 已装环境 workaround
freedesktop 查找顺序 `~/.local/share/icons` > `/usr/share/icons`，用户级同名文件会赢。
写用户级覆盖：
```bash
cp -f <纯 logo 1024x1024> /home/dp25/.local/share/icons/hicolor/256x256/apps/workbuddy.png
chmod 644 .../workbuddy.png
gtk-update-icon-cache -f -t /home/dp25/.local/share/icons/hicolor
```
已写入（`/tmp/icon_old.png` ← 从 `workbuddy_5.3.14-2_amd64_old.deb` 抽出来的 1024x1024 纯 logo）。
dock 可能在重启 dde-dock 后才看到用户级覆盖。

### 下次重打 deb 时
- 新 build-workbuddy.sh 已经会用 Windows 源的纯 logo
- 但装包时 /usr 是否 rw 取决于系统状态；ro 状态下 dpkg 写 /usr/share/icons 也会失败
- postinst 里加一个「写用户级 hicolor」的兜底分支会更稳（避免每次手动覆盖）

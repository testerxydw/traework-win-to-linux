## 图标生成失败修复（本机缺 convert → deb 零图标）

### 现象
用户跑 `bash build.sh` 输出：

```text
>>> 生成图标 ...
  [警告] 缺少 ImageMagick (convert)，跳过图标生成（apt install imagemagick）
```

产物 `trae-solo-cn_0.1.67-1_amd64.deb` 包内 `share/icons` 文件数 = **0**（桌面/菜单无图标）。

### 根因
本机只装了 `imagemagick-7-common`（8:7.1.2.27，**配置文件包**），**没有 ImageMagick 主程序** →
`convert` 与 `magick` 都不存在；`rsvg-convert`（已装 2.58.0）只能处理 SVG；PIL 未安装。
旧脚本 `elif ! command -v convert` → **整段跳过**图标生成。
（注意：图标素材 `trae-icon-256.png`（256×256）一直是有的，缺的是缩放工具。）

### 修复（`build.sh`，commit `ab7f975`）
缩放工具按可用性回退：`convert` → `magick` → **`ffmpeg`** → 原图复制兜底，
并在日志打印实际使用的工具：

```text
>>>   已生成 7 个尺寸 + scalable（缩放工具: ffmpeg）
```

（`workbuddy-win-to-linux/build.sh` 早有"无 convert 则复制原图"兜底，只是尺寸不精确；trae 原本**没有**任何兜底。）

### 验证
重跑 `bash build.sh --no-install --skip-extract` → 产出 `trae-solo-cn_0.1.67-2_amd64.deb`（251M），
包内 8 个 PNG：`16/32/48/64/128/256/512x*/apps/trae-solo-cn.png` + `scalable/apps/...`，
大小 454B → 31KB 递增 → 证明是**真缩放**而非同图复制。
同时提交 `deb-pkg/DEBIAN/control`（版本自增 0.1.67-1 → 0.1.67-2）。

## MCP 服务全部"已关闭"根因与修复（slim 误删跨平台 Node 代码）

### 现象
用户报告「MCP 三个服务（GitHub / gitee / gitlab）全部 Server 已关闭」，弹窗"原始错误信息：扩展进程崩溃或已退出"。

### 根因（已确证）
slim 规则按**任意路径**匹配：`find "$BASE" -path '*win32*' -prune -exec rm -rf {} +`
误删【跨平台 Node 代码】而非平台二进制：
```
node_modules/which/node_modules/isexe/dist/cjs/win32.js
node_modules/which/node_modules/isexe/dist/mjs/win32.js
```
（`isexe/dist/cjs/index.js:32` 有 `require("./win32.js")`，按平台动态加载实现）

→ 扩展宿主启动 `Error: Cannot find module './win32.js'`（MODULE_NOT_FOUND）→ `exit code: 1`
→ `McpService Extension host crashed` / `recovered from crashed, restarting all MCP` 循环
→ 扩展与 MCP 全部不可用；UI 那句"扩展进程崩溃或已退出"**是准确的**。

### 排查中的排除项（避免误判）
| 怀疑点 | 实测结果 |
|---|---|
| 网络不通 | curl 三个 MCP 地址 = 405/401/401（**可达**，非超时）→ 排除 |
| OAuth 未授权 | 日志确有 `authentication failed` / `No token data found`，但那只是**宿主崩溃后的表象** |
| Electron 版本不匹配 | 转制包与官方 `/usr/share/trae-cn` **均为 39.2.7** → 排除 |
| 原生模块是 Windows 版 | 20 个 `.node` **全部 ELF** → 排除 |
| 段错误崩溃 | Crashpad **无转储**，是主动 `exit 1` → 排除 |

### 修复（commit `ce8cf85` + `9103adc`）
1. **规则精确化**：删除一律限定 `-type d`，只删【目录名】带平台后缀的预编译产物目录
   （`win32*`/`msvc*`/`darwin-x64*`/`linux-musl*`/`linux-arm64*`/`linux-armhf*`），不碰同名 `*.js/*.json`
2. **探针**：slim 前/后打印 `isexe/dist/{cjs,mjs}/win32.js` 存在性
3. **终检补回**：slim 末尾若缺失，从官方运行时 `/usr/share/trae-cn` `cp -a` 补回（防复发）
4. workbuddy 的同源规则一并修正（commit `1e1002c`）

### 验证（产物 `trae-solo-cn_0.1.67-5_amd64.deb`）
- 探针输出：`slim 前探针 … 存在` → `slim 后探针 … 保留 ✅`（两个文件）
- 包内容：`cjs/win32.js`(1982B) + `mjs/win32.js`(1806B) 均在 ✅，图标 26 个 ✅

### 待办（第二道坎，尚未修）
`x-scheme-handler/solo-cn` **未注册**（转制包缺 `trae-solo-cn-url-handler.desktop`；官方有 `trae-cn-url-handler.desktop`）
→ MCP 的 OAuth 授权回跳 `solo-cn://…` 无法回到应用，授权可能仍完不成。
修法：`stage_desktop` 生成该 desktop（`Exec=/opt/trae-solo-cn/trae-solo-cn --open-url %U`，

### 附带结论
- 相对 TraeWork 原始树"缺失"的 67 个 `@byted-icube/ai-modules-chat/dist/*.mjs` 属**正常差异**：
  官方 trae-cn 该目录 85 个文件、TraeWork Windows 树 81 个，**hash 文件名不同**，非误删。

## 第二道坎已完成：x-scheme-handler/solo-cn 注册（commit `97d6754`）

上方「### 待办（第二道坎，尚未修）」已落地。**三件事缺一不可**：

1. **新增 `trae-solo-cn-url-handler.desktop`**（`stage_desktop` 生成）：
   `MimeType=x-scheme-handler/solo-cn;`、`Exec=/opt/trae-solo-cn/trae-solo-cn --open-url %U`、`NoDisplay=true`；
   命名必须是 `<desktop 名>-url-handler.desktop`（与官方 `code-url-handler.desktop` /
   `buddycn-url-handler.desktop` / `trae-cn-url-handler.desktop` 同款）。
2. **launcher 里 `export CHROME_DESKTOP=trae-solo-cn-url-handler.desktop`** —— 最关键且最易漏：
   Chromium 的 `setAsDefaultProtocolClient` 通过该环境变量取 desktop 文件名，未设置时在 Linux
   **直接返回 false（静默不注册）**；官方 VS Code 的 `bin/code` 里就有这一行。
3. **postinst 兜底**：为各用户幂等写 `~/.config/mimeapps.list` 的 `x-scheme-handler/solo-cn=`
   （插入 `[Default Applications]` 段；已有该键则跳过），防系统缺 `xdg-settings`/`xdg-mime`。

验证（本机，用户级、无需 root）：`desktop-file-validate` 通过；`gio mime x-scheme-handler/solo-cn`
与 `xdg-mime query default` 均解析到 `trae-solo-cn-url-handler.desktop`；`strings` 确认 Electron
二进制含 `CHROME_DESKTOP`。本机已放 `~/.local/share/applications/trae-solo-cn-url-handler.desktop`
+ `mimeapps.list` L121 注册行 → **当前 -5 安装即可用，无需重装**。

（注：`product.json` 的 `urlProtocol = "solo-cn"`，**不是** `trae-cn`；官方 trae-cn 用的是另一个 scheme。）

## 追加核实：scheme 注册对当前 MCP **不是必需**（用户 2026-09-21 质疑成立）

- 实证：`~/.config/TRAE SOLO CN/User/mcp.json` 里 GitHub MCP 走
  `env.GITHUB_PERSONAL_ACCESS_TOKEN`（**PAT 认证**），完全不经过 OAuth；
  `User/globalStorage/` 下**没有** `github-authentication` 缓存 → 从未用过 URL 回跳。
- 故 commit `97d6754` 对「MCP 能连上、能用」**没有贡献**：
  扩展宿主与 MCP server 的拉起和 URL scheme 无关（之前的崩溃是 slim 误删 `win32.js` 引起）。
- 但它也不是纯废码：`product.json` 有 `urlProtocol: "solo-cn"`、`deeplinkHost: "solo-deeplink.ai"`、
  `trustedExtensionProtocolHandlers: [..., vscode.github-authentication, ...]`，应用启动时确实会执行
  `setAsDefaultProtocolClient(s.urlProtocol, process.execPath, ["--open-url","--"])`；
  官方 trae-cn 也带 `trae-cn-url-handler.desktop`。
  ⇒ 定位是「与官方行为对齐 + 让 `solo-cn://` 深链/OAuth 回跳可用」的**可选补齐**，保留零运行时开销；
  若要最小改动可 `git revert 97d6754`，并删除本机用户级
  `~/.local/share/applications/trae-solo-cn-url-handler.desktop` 与 `mimeapps.list` 中该注册行。
- **教训**：把「疑似缺失的官方行为」列成待办前，先确认**用户实际路径**是否依赖它
  （本例若先看 `mcp.json` 的 PAT 配置，就能正确标注为"可选"而非"MCP 第二道坎"）。
